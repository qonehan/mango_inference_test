v0.9.1 정정 규칙 — 아래 규칙 우선

## 2026-11-17 재검토 반영: 확정 분석 규칙 (v0.9.1)

이 절은 앞 절의 충돌하는 정의보다 우선합니다. v1.0 동결 전 초안이며 본 측정은 실행하지 않았습니다. 구현 기준은 `code/analysis_metrics.py`, 검증은 `code/test_analysis_metrics.py`입니다.

1. **P3 성공률:** W1·W3·W2 각각의 성공률 차이를 1/3씩 가중합니다. W2는 세션을 하나의 이항 관측으로 봅니다. 무실패에서도 0폭 구간이 되는 백분위 부트스트랩을 사용하지 않습니다. 모델별 오류 확률 alpha=0.05/16을 6개 주변 성공률(M·OR × 3작업)에 alpha/6씩 배분하고 각각 양측 Clopper–Pearson 구간을 구합니다. 차이 구간은 [sum(w*(L_M-U_OR)), sum(w*(U_M-L_OR))]입니다. 짝의 의존성과 무관하게 합집합 상계로 보수적으로 보장하며 짝지음의 효율은 포기합니다. 요청·세션 간 독립을 가정하므로 시간 상관은 한계로 보고합니다. 미측정 작업이나 독립 표본이 없는 작업이 있으면 판정 불가입니다. ±2%p 동등 기준은 유지하되 이 예산으로 판정 불가가 나올 수 있음을 명시합니다.

2. **P4 성공 세션당 비용:** 경로별 C=sum(계획된 공통 W2 세션에서 발생한 모든 청구액)/성공 세션 수, 통계량 C_M/C_OR입니다. 실패 세션의 청구액과 중단 전 완료 턴도 포함합니다. 세션 한 턴이 실패하면 그 세션의 나머지 턴은 보내지 않습니다. 비용 미확인은 0으로 채우지 않으며 주 비용 판정은 보류합니다. 성공 0건 또는 OR 비용 0이면 비율 판정 불가입니다. 회차별로 전체 세션 쌍을 재표본하고 매번 비용 합·성공 수를 다시 계산합니다. 분모가 0인 재표본은 삭제하지 않고 전체 비용 구간 판정을 보류합니다. 99.6875% 백분위 구간, 10,000회, 시드 20261116. 양쪽 성공 세션만의 비용 기하평균은 보조 지표로만 보고합니다.

3. **P2 스트림 처리량:** usage 전용·역할·빈 조각을 제외한 첫·마지막 생성 내용(reasoning/content/tool) 조각 시각을 사용합니다. completion이 reasoning을 포함함을 확인하고, reasoning 토큰이 양수인데 reasoning 스트림이 전혀 없거나 보고값이 결측이면 decode는 산출 불가입니다. 생성 내용 조각이 2개 미만, completion<=1, 시간차<=0도 산출 불가입니다. 관측 가능한 경우 (completion-1)/(마지막 생성 내용-첫 생성 내용)로 계산하되 첫 조각에 여러 토큰이 포함되는 근사임을 표시합니다. E2E는 정상 스트림 종료까지의 시간이며 completion/E2E를 모든 경로의 보조 지표로 보고합니다. decode 결측은 0이나 E2E 처리량으로 대체하지 않습니다. 공통 W1 쌍의 어느 쪽이든 구조적으로 decode를 관측할 수 없으면 해당 모델 P2 전체 판정은 보류하고 관측 가능 부분집합 결과만 탐색적으로 보고합니다.

4. **라우팅 구간:** 요청 건수 비중만 Wilson 구간을 사용합니다(독립 요청 가정의 한계 명시). 최종 응답 제공사의 토큰 비중은 회차 × 작업을 층으로 요청 전체를 재표본하며, 매번 제공사별 입력+출력 토큰 합/전체 토큰 합을 재계산합니다(10,000회, 시드 20261116, 95% 구간). 토큰을 독립 시행으로 세지 않습니다. 첫 시도 분포는 요청 건수로만 보고하며 최종 응답 토큰을 첫 시도에 귀속하지 않습니다. 실패·토큰 결측 건수와 미귀속 토큰을 별도 보고하고, 응답·토큰이 확인된 요청에 조건부인 비중임을 명시합니다. 공개 30일 점유율과의 차이는 탐색적 구성 차이일 뿐입니다.

5. **시간 블록:** M·OR 주 비교 W1/W3 질문 쌍 또는 W2 세션 쌍을 하나의 블록으로 배치합니다. 블록마다 두 경로 순서를 시드로 무작위화하고, 모델별 두 요청을 연속 배치합니다. 계정 속도 제한은 준수하며 다른 탐색 요청은 쌍 사이가 아닌 블록 사이에 균등 배치합니다. W2는 세션 쌍 내부에서 각 경로 10턴을 순차 실행합니다. 블록 ID·양쪽 시작 시각·짝 간 시차를 보존하고 시차 분포와 회차별 민감도 분석을 보고합니다. 6시간 회차 안에 있다는 이유만으로 동시 조건으로 취급하지 않습니다.

6. **실패 후 축소:** 실패율 50% 초과여도 M·OR-기본의 공통 W1/W3/W2 주 비교는 예정 수량을 유지합니다. 축소는 탐색용 경로·추가 라우팅 요청에만 적용합니다. 예산·장애로 주 비교 수량을 채우지 못하면 미실행을 서비스 실패로 대입하지 않고 미측정으로 기록하며 해당 모델 전체 기간의 주 판정을 보류합니다. 실행 후 실패와 실행 전 미측정을 구분합니다.

7. **정의 정합성:** W2 주 P1 세션값은 2~10턴 TTFT(content)의 기하평균입니다. 산술평균은 보조 통계입니다. 본 측정용 세션 풀 48개와 파일럿용 별도 6개를 만들고 재사용하지 않습니다. 파일럿 분산 산정은 정밀도 계획용 근사이며 32~48 상한은 검정력 보장이 아닙니다. 일반 JSON 직렬화 전체의 접두부가 아닌 정규화한 메시지 목록의 기존 메시지 불변성과 텍스트 바이트를 검사합니다. 서버 템플릿 이후 토큰 접두부는 직접 확인할 수 없으므로 실제 캐시 적중은 usage로 검증합니다.

client = AsyncOpenAI(base_url=…, api_key=…, max_retries=0,
                     http_client=httpx.AsyncClient(timeout=httpx.Timeout(300.0)))

# OpenRouter 경로만 extra_body로 추가:
"reasoning": {"enabled": true},          # reasoning 켜짐 명시
"trace": {"trace_id": request_id}        # 생성에 영향 없는 메타데이터
  • temperature 1.0, top_p P: 모델 제작사 권장값(Hugging Face 모델 카드, 2026-11-17 확인). P는 DeepSeek 1.0, GLM-5.3·GLM-5.3-Flash·Kimi K3.1 Pro 0.95. 모든 경로에 같은 값. Mango의 DeepSeek·GLM-5.3은 top_p를 지원 목록에 두지 않아 서버 기본값이 적용될 수 있음(지원 파라미터 목록 기록).
  • reasoning은 켜짐 단일 조건. 시험 결과 모든 모델·엔드포인트의 기본값이 켜짐이고 GLM 계열은 끌 수 없음. OpenRouter는 reasoning.enabled=true를 명시, Mango는 공식 조절 파라미터가 없고 기본값이 켜짐이므로 보내지 않음. 강도 조절 등 보조 조건은 두지 않음. 응답마다 reasoning 토큰 수로 확인(7장).
  • 재시도 없음(max_retries=0). 실패한 요청은 다시 보내지 않고 실패로 기록.
  • W2·W3는 아래 4-2의 도구 정의를 tools로 보내고 tool_choice는 "auto".

5실행 구조

5-1. 회차 구성

실험은 회차 8회로 구성합니다. 1~4회차는 단계 1(전체), 5~8회차는 단계 2(제공사 선택만)이며, 회차 시작 간격은 6시간입니다 [기록: 각 회차 시작 UTC]. 그 전에 파일럿 1회를 수행하며 파일럿 데이터는 분석에 쓰지 않습니다.

단계 1 회차당 요청 (모델 1개 기준, W2 세션 수 n = 32일 때)건수
M: W1 15 + W3 15 + W2 (n/4 = 8)세션 × 10턴 + L 3길이 × 2 + Z 8 + 부하 24 + 캐시 대조 4152
OR-기본: W1 75 + W3 75 + W2 8세션 × 10턴 + L 6 + Z 8 + 부하 24268
OR-고정 ×5 각각: W1 15 + W3 15 + W2 2세션 × 10턴 + L 6 + Z 8 + 캐시 대조 45 × 68 = 340
OR-가격·처리량·지연·floor·nitro (5경로) 각각: W1 4 + W3 45 × 8 = 40
합계 (모델 4개면 3,200)800

단계 2 회차는 OR-기본(W1 75 + W3 75)과 정렬 5경로(각 W1 4 + W3 4)만 실행합니다(모델당 190건). 파일럿은 12경로 × 각 작업 5건에 더해, W2 세션 수 산정을 위해 M·OR-기본에 같은 세션 6개씩을 보냅니다. W2 세션 수 n은 파일럿에서 모델마다 세션별 로그 비율(M ÷ OR-기본)의 표준편차 s를 구해 n = ceil((2.96 × s / 0.05)²)를 4의 배수로 올리고 32~48로 제한합니다 [기록: 모델별 s와 n]. 품질 점검 회차는 본 회차와 겹치지 않는 시간에 1회, Q 400문항 × 6경로(M, OR-고정 ×5) × 4모델 = 9,600건을 실행합니다.

5-2. 질문 배정 (같은 질문을 모든 경로에)

slot_seed = int(sha256(f"v0.9|slot{n}").hexdigest()[:16], 16)

C_s  = rng.sample(W2_s, 2)       # 캐시 대조: 각 세션의 6턴 입력을 ① 새 nonce ② 같은 nonce로 즉시 재전송 (M·OR-고정)
L_s  = 길이별로 rng.sample(L_pool[len], 2)
Load = W1_s[:24]

같은 회차에서 같은 질문 ID는 모든 경로에 같은 내용(nonce만 다름)으로 보냅니다.

5-3. 실행 순서 (회차 1회)

  1. 시작 기록: 환경, 코드 커밋, 질문 파일 해시, 시각 오차, 호스트 IP·ASN·traceroute.
  2. 연결 측정: 호스트(Mango, OpenRouter)마다 새 TCP+TLS 연결 10회, 연결·핸드셰이크 시간 기록. 대조군 측정(60초마다 두 호스트 TCP 연결 시간) 시작.
  3. 준비 호출: 작업자마다 Z 1건 (분석 제외, 연결을 열어 두기 위함).
  4. 본 루프: 모델 × 경로마다 작업자 1개. 작업자는 자기 요청 목록을 random.Random(slot_seed + 작업자 번호)로 섞은 순서대로 한 번에 1건씩 보냄. 전체 동시 요청은 세마포어로 최대 16. W2는 한 세션의 10턴을 순서대로 연속 실행. 모델별 OpenRouter 호출은 분당 18회 이하(새 계정 한도 분당 20회 대응). Mango 호출은 4개 모델 합계 동시 3건·분당 36회 이하(기본 등급 키당 동시 4·분당 40, 실행 시점 등급 기록).
  5. 부하 조건: 본 루프 종료 후, M과 OR-기본에 대해 W1 24건을 동시 4건씩 6묶음(Mango 기본 등급의 키당 동시 한도 4).
  6. 서버 기록 조회: 마지막 요청 60초 후, OpenRouter 응답마다 GET https://openrouter.ai/api/v1/generation?id=<응답 id>. 404면 30초 간격 최대 5회 재조회.
  7. 점검·봉인: 8장 점검 실행, 모든 파일의 SHA-256을 manifest.json에 기록.

OpenRouter Broadcast는 VM의 HTTPS 수신 주소로 계속 받아 날짜별 파일에 추가합니다. 결합 키는 trace_id = 요청 ID입니다.

6측정 방법

  • 시계: time.perf_counter_ns(). t0 = create() 호출 직전.
  • 조각 기록: 스트림 조각마다 도착 시각과 종류를 기록. 종류: reasoning(delta.reasoning 또는 delta.reasoning_content에 내용), content(delta.content), tool(delta.tool_calls).
  • 토큰 수: 마지막 조각의 usage (prompt, cached, completion, reasoning). reasoning은 completion_tokens_details.reasoning_tokens 또는 usage.reasoning_tokens(모델마다 다름). 조각 개수로 세지 않음.
  • 비용: OpenRouter는 generation 조회의 total_cost. Mango는 응답에 비용이 없어 토큰 수 × GET /v1/models의 cost(회차마다 스냅샷)로 계산하고 콘솔 청구 내역 합계와 대조 [기록].
  • 버전·지원 기능: 회차마다 모델 버전(OpenRouter permaslug, Mango weight_version)과 엔드포인트 정보(양자화, 지원 파라미터, 자동 캐시 지원 supports_implicit_caching) 스냅샷.
  • 엔드포인트: generation 조회의 provider_responses[].endpoint_id를 OpenRouter 공개 엔드포인트 목록(/api/frontend/v1/stats/endpoint?permaslug=…)과 대조해 슬러그·양자화·지역·서비스 등급·단가 기록.
  • 응답 보존: 응답 헤더 전체, 최종 텍스트, 도구 호출 JSON, finish_reason.

8품질 점검과 제외 규칙

8-1. 파일럿 합격 기준 (모두 충족 시 설정 동결 → v1.0)

  • 모든 경로 × 모델에서 성공 5건 이상, 필수 필드 결측 0건.
  • OpenRouter 요청의 generation 조회·Broadcast 결합률 ≥ 99%.
  • 측정 토큰 수 = 서버 usage, 청구 합계가 계정 청구 내역과 ±2% 이내.
  • 측정기 검증(로컬 모의 스트림 서버): 정해진 간격으로 조각을 보내는 모의 서버에 동시 1·16 조건으로 호출해 측정 시각 오차 중앙값 < 5ms. 느리게 끝나는 스트림에서 요청 전체 마감 300초가 지켜짐. 실제 서비스는 허용 동시성 안에서만 호출.
  • W2 세션 파일 접두부 일치 검사 통과, 모델별 s와 n 계산.
  • finish_reason = length 비율 ≤ 1%. 넘으면 max_tokens 상한을 올려 재시험.

9분석 절차

  1. 결합: 요청 ID로 측정 기록 · generation 조회 · Broadcast를 결합. 결합되지 않은 행 수를 보고.
  2. 기술 통계: 셀(모델 × 경로 × 작업)별 p50·p90·p99와 회차별 중앙값. 판정에는 쓰지 않음.
  3. 주 비교 16개: 모델 4 × 지표 4, Mango(M) vs OR-기본.
    P1 응답 속도P2 생성 속도P3 성공률P4 비용
    W2 세션값(2~10턴 TTFTcontent 기하평균), 세션 쌍 n개W1 공통 질문 decode 처리량, 회차당 15쌍공통 요청 묶음(W1 공통·W3 공통·W2 세션 각 1/3 가중)W2 성공 세션당 비용, 세션 쌍
  4. 통계량 (하나로 고정): P1·P2·P4는 짝 단위(세션 ID·질문 ID)별 log(M ÷ OR-기본)의 평균을 지수화한 기하평균 비율(양쪽 성공 쌍만). P3는 절대 차이(%p) = M 성공률 − OR-기본 성공률. 신뢰구간은 회차를 층으로 짝 단위를 복원추출 10,000회, 시드 20261116, Bonferroni 백분위 수준 1 − 0.05/16 = 99.6875%.
  5. 판정: P1·P4는 구간 전체 < 0.90 우위, > 1.10 열위, 0.90~1.10 안 동등. P2는 방향을 뒤집음. P3는 구간 전체 > +2%p 우위, < −2%p 열위, ±2%p 안 동등. 그 외 판정 불가. 경로별 실패율과 실패 유형(5xx, 제공사 429, 마감 초과, 스트림 중단, 잘림, 도구 인자 오류)을 함께 보고.
  6. 배분 분포 (B): OR-기본의 W1·W3 요청에서 첫 시도와 최종 응답의 비율을 엔드포인트 단위와 제공사 단위로, 요청 건수 기준과 토큰 기준으로 각각 집계, Wilson 95% 신뢰구간. 30일 점유율(data/openrouter_monthly_share_final_20261116.csv)은 제공사 단위로만 공개되므로 비교는 제공사 단위로 하고, 기준값이 신뢰구간 밖이면 "차이 있음". 결론은 "이 계정·작업의 기본 배분이 공개 사용량 구성과 다르다"까지로 제한(사용자 선택의 증거로 해석하지 않음). 정렬 경로는 경로별 최빈 엔드포인트와 순위.
  7. 공개 통계 대조: OR-고정 측정값의 순위를 같은 엔드포인트의 공개 1주 통계(본 실행 시점 재수집)와 비교. 제공사 가중평균 값은 쓰지 않음.
  8. 길이에 따른 관측 지연 (탐색): 경로 × 모델마다 L·Z의 첫 토큰 시간(TTFTany) 중앙값과 입력 토큰에 대한 최소제곱 기울기를 "관측 지연 증가율"로 보고. reasoning 토큰은 있는데 스트림에 reasoning 내용이 없는 엔드포인트는 제외. 서버 내부(prefill·대기열·내부 네트워크)로 분해하지 않으며, Broadcast 구간 시간은 OpenRouter 기술 통계로만 사용.
  9. 캐시 대조: 경로별 ② ÷ ① 첫 답변 시간의 기하평균 비율과 ②의 캐시 적중률. W2 턴별 캐시 적중률도 보고.
  10. 품질 점검: 같은 문항에 대한 Mango와 각 고정 엔드포인트의 정답 여부를 짝지어 비교(McNemar 검정, 차이의 95% 구간). 같은 모델에서 정답률이 6경로 중앙값보다 10%p 이상 낮은 경로는 성능 결과에 표시. 4비트 계열과 8비트의 차이는 탐색적으로 보고(신고 양자화 기준).
  11. 부 비교 (탐색): M vs OR-고정 각각(W2는 8세션), 부하 조건, p90, 실패 반영 처리량. 같은 통계량, 보정 없이 95% 구간.
