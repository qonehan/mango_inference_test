# 실험 계획 절차

이 실험을 어떤 순서로 계획했고, 앞으로 어떤 순서로 진행하는지 정리합니다. 같은 종류의 실험(추론 API 제공사 성능 비교)을 다시 설계할 때 체크리스트로 쓸 수 있게 단계마다 산출물과 판단 기준을 적었습니다.

## 전체 흐름

```
① 질문 정의 → ② 배경 조사 → ③ 사전 등록 초안 → ④ 외부 방법론 검토
      → ⑤ 간이 테스트 → ⑥ 변수별 통제 시험 → ⑦ 프로토콜 보완(반복)
      → ⑧ 파일럿 → ⑨ 설정 동결(v1.0) → ⑩ 본 측정 → ⑪ 분석·보고
                                  (현재 위치: ⑦ 완료, ⑧ 준비 중)
```

## 단계별 내용

| 단계 | 한 일 | 산출물 | 넘어가는 기준 |
|---|---|---|---|
| ① 질문 정의 | 같은 모델을 어디서 부르느냐에 따른 성능·비용 차이와 OpenRouter의 제공사 선택을 사용자 관점 질문으로 정의. 성능(RQ1·2)과 제공사 선택(RQ3·4) | [프로토콜](02_실험_프로토콜.md) 1절 | 질문마다 측정 가능한 지표가 있음 |
| ② 배경 조사 | OpenRouter 라우팅 공식 문서, 공개 점유율·성능·가격 수집, Mango 문서·가격 | [라우팅 방식](07_참고_OpenRouter_라우팅_방식.md), [엔드포인트 통계](../data/openrouter_endpoint_stats_20261116.csv) | 비교 대상(모델·제공사·엔드포인트)을 근거로 고를 수 있음 |
| ③ 사전 등록 초안 | 가설·지표 정의·판정 기준(±10% 동등 범위)·제외 규칙·분석 방법을 데이터 보기 전에 고정 | [프로토콜](02_실험_프로토콜.md) v0.9 | 결과를 보기 전에 판정 방법이 정해짐 |
| ④ 외부 방법론 검토 | Artificial Analysis 방법론 정독. 수치는 섞지 않고 방법만 차용(프롬프트 다양화, 멀티턴 작업, 실패 처리 등) | [AA 방법론 정리](06_참고_ArtificialAnalysis_방법론.md) | 차용할 것과 따르지 않을 것이 구분됨 |
| ⑤ 간이 테스트 | 모든 호출 경로를 한 번씩 호출(56건). 경로·응답 형식·기록 항목 확인 | [간이 테스트 결과](03_간이테스트_결과.md) | 모든 경로가 응답하고 필요한 필드가 기록됨 |
| ⑥ 변수별 통제 시험 | 간이 테스트에서 드러난 통제 안 되는 변수를 따로 시험(reasoning 설정 192건) | [reasoning 설정 시험](04_reasoning설정_시험.md) | 각 변수를 어떻게 통제할지 근거가 생김 |
| ⑦ 프로토콜 보완 | 시험 결과로 통제 방식·기록 항목·실행 제약을 반영. 대시보드·콘솔 값과 기록을 대조 | [보완 이력](05_간이테스트_이후_보완.md) | 알려진 교란 변수마다 통제 또는 기록 방법이 있음 |
| ⑧ 파일럿 | 서울 VM에서 경로 × 작업별 5회(약 1,100건). 합격 기준 점검 | (예정) | 합격 기준 전부 충족 |
| ⑨ 설정 동결 | 파일럿 결과로 설정값을 조정하고 v1.0으로 고정, 제3자 검토 기록 | (예정) | 검토자 확인, 이후 변경은 이탈 기록 |
| ⑩ 본 측정 | 품질 점검 1회 + 6시간 간격 8회차 | (예정) | 실행 중 점검 규칙 준수 |
| ⑪ 분석·보고 | 사전 등록한 방법으로 판정, 불리한 결과도 같은 형식으로 보고 | (예정) | – |

## ⑤~⑦에서 실제로 바뀐 것 (요약)

간이 테스트와 후속 시험이 계획을 여러 번 바꿨습니다. 자세한 근거는 [보완 이력](05_간이테스트_이후_보완.md)에 있습니다.

| 발견 | 바뀐 계획 |
|---|---|
| 같은 질문에 reasoning 토큰이 엔드포인트마다 0~599개 | reasoning "켜짐"을 명시하고 토큰 수로 확인 |
| 같은 제공사도 엔드포인트마다 가격·양자화가 다름 | 고정 경로를 제공사가 아니라 엔드포인트 슬러그로 |
| OpenRouter 계정 설정 "Paid model training" 차단이 DeepSeek 공식을 후보에서 제외 | 설정을 허용으로 바꾸고 사전 조건에 추가 |
| OpenRouter 새 계정 한도(모델당 분당 20회), Mango 기본 등급 한도(동시 4·분당 40) | 호출 속도 제한, 부하 조건을 동시 4로 |
| Mango 응답에 비용이 없음, 실제 청구는 할인 전 단가와 일치 | 토큰 × API 단가로 계산, 콘솔 잔액 3회 대조 |
| 템플릿의 기본 시스템 문구가 nonce보다 앞에 와서 캐시됨 | nonce를 첫 시스템 메시지로 |
| 품질 점검 20문항으로는 양자화 차이를 못 잡음 | 400문항, 짝지은 비교 |

## 체크리스트 (다음 실험에 재사용)

**설계**
- [ ] 질문을 사용자 관점의 측정 가능한 지표로 바꿨는가
- [ ] 판정 기준(동등 범위, 다중 비교 보정)을 데이터 보기 전에 정했는가
- [ ] 비교 대상을 제공사가 아니라 엔드포인트 단위로 정의했는가
- [ ] 외부 벤치마크와 수치를 섞지 않는다는 규칙이 있는가

**통제할 변수**
- [ ] 질문: 모든 경로에 같은 질문(짝지은 설계), 출력 종류를 섞은 풀
- [ ] 캐시: 첫 시스템 메시지의 nonce, 세션 안 캐시만 허용, 캐시 토큰 기록
- [ ] reasoning: 모드 명시, 토큰 수로 확인
- [ ] 샘플링: 제작사 권장값, 모든 경로 동일, 지원 파라미터 기록
- [ ] 엔드포인트·양자화·모델 버전: 고정·기록(양자화는 맞추지 않음)
- [ ] 위치·시간: 고정 VM, 클라우드 사업자 편향 확인, 하루를 고르게 덮는 회차
- [ ] 호출 한도: 양쪽 계정 한도 안에서 실행, 한도 429는 우리 쪽 실패

**측정·검증**
- [ ] 클라이언트 측정을 원본으로, 서버 측 기록은 검증용
- [ ] 대시보드·콘솔 값과 기록을 대조(토큰 수, 비용)
- [ ] 품질 점검으로 속도·가격과 품질의 교환을 함께 보고
- [ ] 원시 기록·코드·질문 세트를 해시와 함께 보존
