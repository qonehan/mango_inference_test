# Artificial Analysis 성능 측정 방법론 정리

확인일: 2026-11-16. 활용: [19 실험 프로토콜](02_실험_프로토콜.md) 7-3절 (참고 자료로만 사용)

Artificial Analysis(이하 AA)는 같은 모델을 여러 API 제공사에서 불러 속도·지연·오류·비용을 비교하는 독립 벤치마크입니다. 우리 실험과 같은 방식으로 측정할 수 있는지 검토하려고 방법론 페이지를 읽었습니다. 원문을 복제하지 않고 요약했습니다.

## 1. 읽은 페이지

| 페이지 | 읽은 범위 |
|---|---|
| [Performance Benchmarking](https://artificialanalysis.ai/methodology/performance-benchmarking) | 전문 (핵심 페이지) |
| [Methodology](https://artificialanalysis.ai/methodology) | 전문 (가격·작업당 비용·작업당 시간 정의) |
| [System Load Test](https://artificialanalysis.ai/methodology/system-load-test), [AgentPerf](https://artificialanalysis.ai/methodology/agentperf) | 전문. 하드웨어 벤치마크라 API 측정과는 별개 |
| [Endpoint Accuracy Index](https://artificialanalysis.ai/methodology/endpoint-accuracy-index), [Coding Agents](https://artificialanalysis.ai/methodology/coding-agents-benchmarking) | 전문. 정확도·코딩 에이전트 지표 |
| [Intelligence Benchmarking](https://artificialanalysis.ai/methodology/intelligence-benchmarking) | 앞부분만. 버전 이력·부록은 읽지 않음 |

## 2. 공개된 측정 방식 (Performance Benchmarking, 버전 3.0.0, 2026-11-03)

| 항목 | 내용 |
|---|---|
| 작업 | 입력 약 1k·10k·100k 토큰의 단일 요청, 그리고 AA의 코딩·지식 업무·자동화 평가에서 가져온 멀티턴 에이전트 작업(도구 호출 포함) |
| 프롬프트 | 큰 프롬프트 세트에서 회차마다 뽑아 모든 엔드포인트에 같은 것을 보냄. 출력 종류에 따라 속도가 달라지므로(추측 디코딩 등) 다양성을 둠 |
| 부하 | 모든 작업을 동시 부하 상태에서 측정. 같은 지속 부하를 모든 작업에 적용 |
| 주기 | 6시간마다 (구형 모델 18시간). 이전 버전은 3시간마다 |
| 위치 | Google Cloud Run, 미국 중부(`us-central1`). 위치가 일부 제공사에 유리하거나 불리할 수 있다고 한계로 명시, 측정 지역 추가를 검토 중이라고 함 |
| 클라이언트 | OpenAI 호환 제공사는 OpenAI 공식 Python 라이브러리 |
| 설정 | reasoning 모델 temperature 0.6, 그 외 0. top_p 1. max_tokens는 엔드포인트 출력 한도까지(상한 65,536, 길게 추론하는 엔드포인트는 128,000) |

### 지표 정의

| 지표 | 정의 |
|---|---|
| 첫 토큰 시간 | 요청 송신부터 첫 토큰까지. reasoning 모델은 첫 reasoning 토큰 |
| 첫 답변 토큰 시간 | 요청 송신부터 첫 답변 토큰까지. reasoning 시간 포함 |
| 출력 속도 | reasoning 포함 출력 토큰 ÷ 요청 송신부터 마지막 토큰까지의 시간. 첫 토큰 대기를 포함. 멀티턴은 도구 실행 시간을 뺌 |
| 전체 소요 시간 | 요청 송신부터 마지막 토큰까지 |
| 오류율 | 최근 5일 요청 중 엔드포인트 쪽 실패 비율. 멀티턴 세션은 하나라도 실패하면 실패 |
| 캐시 적중률 | 멀티턴 세션에서 제공사 API가 보고한 캐시 읽기 비율 |
| 출력 토큰 수 | 제공사 API가 보고한 값 (이전 버전은 tiktoken o200k_base로 계산) |

### 집계와 실패 처리

- 회차마다 작업별 중앙값 → 최근 5일 회차 중앙값의 평균. 대표값은 작업들을 같은 비중으로 평균.
- 엔드포인트 쪽 실패(서버 오류, 429, 타임아웃, 마감 시각까지 끝나지 않은 요청)는 출력 속도 0으로 계산하고 오류율에 포함.
- AA 쪽 실패(잘못된 키, 잔액·한도 소진, 형식 오류나 문맥 길이 초과로 거절된 요청, max_tokens로 답변 전에 잘린 응답, 안전 차단)는 제외.

### 계정과 공정성 규칙

- 익명 계정, 크레딧 계정, 벤치마크용으로 받은 키를 섞어 씀. 익명이 아닌 계정을 쓸 때는 별도 익명 계정으로 조작 여부를 검증.
- 제공사는 AA 트래픽을 알아채거나, 전용 자원으로 보내거나, 공개 사양과 다른 모델·양자화·부하 조건으로 처리하면 안 됨. 위반 시 측정 보류, 목록 제외, 공개 등의 조치.
- 제공사 등재는 AA가 자체 판단으로 결정. 등재 신청 절차는 페이지에 없음.

## 3. 공개되지 않은 것 (재현을 막는 요소)

1. **동시 부하 수준**(동시 요청 수, 요청률, 회차당 요청 수, 회차 시간 제한). 부하에 따라 속도가 크게 달라져 가장 큰 걸림돌.
2. 프롬프트 세트의 이름·내용·공개 여부, 입력 길이를 맞추는 방법.
3. 작업별 출력 길이.
4. 요청마다 프롬프트를 바꾸는지, 캐시를 어떻게 다루는지.
5. 멀티턴 작업의 턴 수, 도구 정의, 세션 수.
6. 스트리밍 여부(지표상 사용으로 보이나 명시 없음), 모델별 reasoning 강도.
7. 시간 측정 방식(클라이언트 또는 서버 시계), 실패 요청의 첫 토큰·전체 시간 처리.
8. 측정 코드 공개 여부.
9. 여러 지역을 가진 엔드포인트의 경로.

## 4. 결론: 참고 자료로만 사용

동시 부하, 프롬프트, 멀티턴 작업처럼 결과를 크게 좌우하는 변인이 공개되지 않아 **AA와 같은 조건을 만들 수 없습니다.** 그래서 Mango와 다른 제공사의 비교는 변인을 모두 통제한 우리 실험으로만 하고, AA 수치는 우리 결과와 나란히 놓거나 환산하지 않습니다. 다만 다음 용도로는 참고할 수 있습니다.

- 지표 정의와 실패 처리 규칙이 업계에서 어떻게 쓰이는지 확인 (우리 지표 정의 점검).
- 같은 제공사들 사이의 순위가 대체로 비슷한 방향인지 정성적으로 확인.
- AA에 Mango가 등재되지 않았다는 사실 자체. 2026-11-16 기준 DeepSeek V4.1 Flash·1017 제공사 목록에 Mango 없음. GLM-5.3, GLM-5.3-Flash, Kimi K3.1 Pro의 제공사 페이지는 확인하지 못함.
