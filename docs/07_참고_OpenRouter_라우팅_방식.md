# OpenRouter 제공사 라우팅 방식 정리

작성일: 2026-11-16. 관련: [실험 프로토콜](02_실험_프로토콜.md)

OpenRouter 공식 문서 두 개를 읽고, 한 요청이 어느 제공사로 가는지를 **기본 자동 배분**과 **사용자 지정**으로 나눠 정리했습니다. 두 페이지 모두 갱신일 표시가 없어 확인일(2026-11-16)만 적습니다. **2026-11-17에 원문과 다시 대조했고, 프롬프트 캐시 문서도 추가로 읽었습니다(6절).** 원문을 복제하지 않고 요약했습니다.

| 출처 | 다루는 내용 |
|---|---|
| [Traffic Routing](https://openrouter.ai/docs/guides/providers/traffic-routing) | OpenRouter가 직접 고를 때 엔드포인트별 트래픽 몫을 정하는 방식 (제공사 관점) |
| [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection) | 요청의 `provider` 객체·단축 접미사·계정 설정·BYOK로 사용자가 제어하는 방식 |

## 1. 요약

- **기본값은 가중 무작위 배분입니다.** 몫은 **보정 가격과 속도 두 축**으로 정합니다. 보정 가격은 실효 가격에 첫 토큰 시간·오류·429·도구 호출 품질을 더한 값이고, 속도(첫 토큰 대기를 포함한 종단간 초당 출력)는 가격과 맞바꾸는 별도 축입니다. 빠른 엔드포인트는 보정 가격이 더 높아도 경쟁권에 남습니다. 요청마다 몫에 비례해 무작위로 뽑습니다(2026-11-17 대조로 정정).
- **1등 근처면 대부분을 나눠 받고, 경쟁 가장자리 밖은 급감합니다.** 다만 0은 아니어서 개선을 감지할 탐색 트래픽은 계속 받습니다.
- **기본 배분을 건너뛰는 경우는 네 가지입니다.** `sort`(요청 또는 계정 기본값), `:floor`/`:nitro`, `order`, 자기 제공사 키(BYOK). `only`/`ignore`는 남는 제공사가 2곳 이상이면 그 안에서 여전히 기본 배분을 씁니다.
- **공개 통계로는 두 경로의 비율을 나눌 수 없습니다.** 문서도 비율을 공개하지 않습니다. 월간 제공사 통계([data](../data/openrouter_monthly_share_final_20261116.csv))의 점유율은 두 경로가 섞인 결과입니다.

## 2. 요청 한 건의 경로

```
요청 ─▶ ① 후보 거르기 (계정 설정 + 요청 필터)
         계정 허용·제외 목록, 데이터 정책·ZDR, only/ignore,
         require_parameters, quantizations, max_price, 도구·출력 길이 지원
      ─▶ ② 순서 정하기
         ├─ sort · :floor · :nitro · order · BYOK 있음 ─▶ 지정한 순서대로 시도
         └─ 없음 ─▶ 기본 배분: 보정 가격으로 몫 계산 → 가중 무작위 선택
      ─▶ ③ 실패 시 남은 후보에서 같은 방식으로 재선택 (allow_fallbacks=false면 중단)
```

프롬프트 캐시가 따뜻한 동안 후속 요청은 같은 제공사에 머뭅니다. 고착 규칙의 상세는 프롬프트 캐시 문서에 있습니다(6절).

## 3. 기본 자동 배분 (Traffic Routing)

### 3-1. 입력 지표

모두 최근 실제 트래픽에서 측정하며 최근 몇 분의 비중이 가장 큽니다. 트래픽이 적은 엔드포인트는 비슷한 제공사의 평균값에서 시작합니다.

| 지표 | 정의 | 보정 가격 반영 (문서 예시) |
|---|---|---|
| 실효 가격 | 최근 30분 실제 청구액. 캐시 적중률·입출력 비율 반영 | 요청당 예상 토큰 × 실효 단가 (약 $0.142) |
| 속도 | 첫 토큰 대기를 포함한 초당 출력 토큰 | 가격에 더하지 않고 **가격과 맞바꾸는 별도 축**. "경쟁 가장자리"가 속도에 따라 위로 휘어 빠를수록 더 비싸도 경쟁권. 예: 5초 대기 + 5초간 500토큰 = 50 tok/s |
| 첫 토큰 시간(TTFT) | 첫 토큰까지의 시간 | 속도와 별도로 가격에 직접 가산 (대화형·에이전트 용도) |
| 신뢰성 | 엔드포인트 탓의 실패 | 오류율 1% × 페널티 8배 ≈ 가격 +8% |
| 품질 | 형식이 올바른 도구 호출 응답 비율 | 95%면 가격 약 +5% |
| 429 | 거절 후 다른 곳으로 재전송하는 대기 | 대기 비용+페널티를 429 비율로 가중 ($2.50 × 0.4% ≈ +$0.01) |

| 신뢰성 오류로 셈 | 세지 않음 |
|---|---|
| 5xx, 응답 없음(연결 끊김·타임아웃), 설정 오류(401·402·404·405·408·410·421·423·424·426·498), 중간 실패 | 400·413·422, 지역·법적 차단(403·451), 사용자 종료(499), 429(별도 계산) |

### 3-2. 안전장치

- **차단:** 신뢰성·품질·429가 같은 모델의 다른 제공사보다 훨씬 나쁘면 회복할 때까지 트래픽 0.
- **단기 후퇴:** 429 급증·지연 급등 시 그동안 몫을 잠시 낮춤.
- **용량 학습:** 429가 나기 전에 제공사별 용량을 학습해 넘치는 몫을 다른 곳으로 보냄.
- **품질 표시:** 도구 호출이 깨졌거나 벤치마크 정확도가 기대보다 크게 낮으면 표시가 풀릴 때까지 탐색 트래픽만.

수치 공식(예: 가격의 역제곱 가중)은 두 문서 어디에도 없습니다. 몫 곡선은 정성적으로만 설명돼 있습니다.

## 4. 사용자 제어 (Provider Routing)

### 4-1. `provider` 객체 필드

| 필드 | 기본값 | 효과 | 분류 |
|---|---|---|---|
| `order` | - | 제공사 슬러그를 순서대로 시도. 이름 붙인 제공사에선 BYOK 우선순위보다 앞섬 | 순서 지정 (기본 배분 우회) |
| `allow_fallbacks` | true | false면 지정한 곳 외 예비 제공사 사용 안 함. `order` 없이 false면 1순위 엔드포인트만 | 폴백 |
| `sort` | - | `"price"`·`"throughput"`·`"latency"` 또는 `{by, partition}` | 순서 지정 (기본 배분 우회) |
| `only` / `ignore` | - | 허용·제외 슬러그 | 필터 (2곳 이상 남으면 기본 배분 유지) |
| `require_parameters` | false | true면 요청 파라미터를 모두 지원하는 제공사만 | 필터 |
| `data_collection` | "allow" | "deny"면 사용자 데이터를 수집하지 않는 제공사만 | 필터 |
| `zdr` | - | true면 ZDR 엔드포인트만 (Safety Retention 엔드포인트도 허용, 단 계정·가드레일이 "ZDR only"면 제외) | 필터 |
| `enforce_distillable_text` | - | true면 모델 작성자가 텍스트 증류를 허용한 모델만 | 필터 |
| `quantizations` | - | 양자화 수준 필터 (int4·int8·fp4·fp8·fp16·bf16 등) | 필터 |
| `max_price` | - | 100만 토큰당 `prompt`·`completion` 상한 (선택: `request`, `image`). 맞는 가격이 없으면 요청 실행 안 함 | 필터 (하드) |
| `preferred_min_throughput` | - | tok/s 하한. 숫자는 p50, 객체는 p50·p75·p90·p99 | 선호 (소프트) |
| `preferred_max_latency` | - | 초 단위 상한. 위와 동일 | 선호 (소프트) |

선호 조건은 최근 5분 이동 창의 모델·제공사별 백분위로 판단합니다. 미달 엔드포인트는 **제외되지 않고 목록 끝으로** 밀립니다. 조건을 여러 개 주면 모두 충족해야 우선 그룹에 듭니다.

### 4-2. 정렬과 단축 접미사

| 방법 | 동작 |
|---|---|
| `sort: "price"` / `"throughput"` / `"latency"` | 최저가 / 최고 처리량 / 최저 지연 순서로 시도 |
| `sort: {by, partition: "model"}` (기본) | 폴백 모델이 있어도 1순위 모델의 엔드포인트를 먼저 시도 |
| `sort: {by, partition: "none"}` | 나열한 모든 모델의 엔드포인트를 한 줄로 정렬 |
| `모델:floor` | 가격 정렬 + flex 서비스 등급 엔드포인트 포함 |
| `모델:nitro` | 처리량 정렬 + priority 서비스 등급 엔드포인트 포함 |

### 4-3. 엔드포인트 지정

- 슬러그 형식은 `provider[/variant][/region][/tier]`입니다. 기본 슬러그(`google-vertex`)는 그 제공사의 변형·리전 엔드포인트를 모두 포함하고, 구체 슬러그(`deepinfra/turbo`)는 하나만 지정합니다.
- 기본 슬러그만으로는 서비스 등급 엔드포인트(`openai/fast`, `google-vertex/flex` 등)에 들어가지 않습니다. `service_tier`나 접미사 슬러그가 필요합니다. 오픈웨이트 모델의 priority 엔드포인트는 예외로 기본 풀에 있습니다.
- 비공개 엔드포인트: `order`를 주고 `allow_fallbacks: false`면 `order` 제공사 → 자기 비공개 엔드포인트 → (다른 공개 제공사 없음) 순서입니다.

### 4-4. 계정 설정과 요청 설정의 관계

| 계정 설정 (`/settings/preferences`, `/settings/privacy`) | 요청 설정과의 관계 |
|---|---|
| 기본 제공사 정렬 | 설정하면 기본 배분 우회. 요청 `sort`가 이를 덮어쓰는지는 문서에 없음 |
| 허용 제공사 | API·채팅방 전체에 적용. 요청 `only`는 이 범위 안에서만 좁힘. 교집합이 없으면 404 |
| 제외 제공사 | 요청 `ignore`와 합집합 |
| 데이터 정책 | `data_collection`의 계정 단위 버전 |
| ZDR (모델 그룹별 또는 가드레일) | 요청 `zdr`과 OR. 요청으로 켤 수는 있어도 계정·가드레일 설정을 끌 수는 없음 |

### 4-5. BYOK와 기타

- 자기 키가 있는 제공사는 `order`가 없으면 자동 우선입니다. `order`가 있으면 그 순서를 따르되 각 제공사 안에서 자기 키를 공유 용량보다 먼저 씁니다.
- `require_parameters: false`일 때도 도구, 응답 형식(구조화 출력 포함), verbosity는 소프트 선호로 작동합니다. 일부 제공사만 지원하면 그곳으로만 가고, 아무도 지원하지 않으면 파라미터를 무시합니다.
- 리전 데이터 보관은 Business·Enterprise 전용으로, `eu.openrouter.ai` 또는 `us.openrouter.ai` 주소로 보냅니다.
- 문서에 없는 것: 프리셋 설명, 모델 폴백(`models`) 상세(별도 페이지), 계정 정렬과 요청 정렬의 충돌 규칙.

## 5. 기본 배분이 적용되는 범위

| 경로 | 기본 배분 | 근거 |
|---|---|---|
| 아무 설정 없음 | 적용 | 두 문서 |
| `only`/`ignore`/데이터 정책 등 필터 후 2곳 이상 남음 | 남은 후보 안에서 적용 | Provider Routing |
| 필터 후 1곳만 남음 | 미적용 (그곳으로) | Traffic Routing |
| `order` 지정 | 미적용 | 두 문서 |
| `sort`(요청 또는 계정 기본값), `:floor`, `:nitro` | 미적용 | 두 문서 |
| BYOK | 미적용 | 두 문서 |
| `preferred_*` 선호 조건 | 문서상 명시 없음. 미달 엔드포인트를 뒤로 미는 정렬로 설명됨 | Provider Routing |
| 모델 라우터(Auto Router 등) | 적용. 라우터가 모델을 고른 뒤 그 모델의 제공사는 직접 요청과 같은 규칙(기본 배분과 `provider` 설정)으로 고름 | Routers 개요·Auto Router (5-1절) |


### 5-1. 모델 라우터와 모델 폴백 (2026-11-18 추가)

라우터는 제공사가 아니라 **모델**을 고르는 장치입니다. 모델이 정해지면 그 모델의 제공사는 직접 요청과 같은 규칙으로 고릅니다. Routers 개요 문서에 "라우터가 모델을 고르면 직접 요청과 같은 방식으로 사용자의 제공사 선호에 따라 제공사를 고른다"고 적혀 있습니다. Auto Router 문서도 `provider.max_price`가 라우터가 고른 모델의 엔드포인트에 적용된다고 밝힙니다. 라우터 수수료는 없고, 선택된 모델의 요금만 청구됩니다.

| 라우터 | 모델 ID | 동작 | 설정 |
|---|---|---|---|
| Auto Router | `openrouter/auto` | 요청마다 모델과 추론 강도를 고름. ① 데이터 정책·모델 기능·제공사 제한·BYOK·허용·제외 목록으로 후보를 거르고, ② 빠른 판단 모델이 요청을 11개 항목으로 평가하고, ③ 실시간 가격·캐시 상태·벤치마크를 비용 등급 안에서 저울질함. 같은 대화에서는 모델 교체를 자제하고 추론 강도부터 조정함 | `plugins: [{id: "auto-router", allowed_models, excluded_models, cost_tier}]`. 계정 기본값은 Routing 설정 화면에 저장 |
| Auto Code / Auto Beta | `openrouter/auto-code`, `openrouter/auto-beta` | 코딩 에이전트용 Auto / 실험판(설정의 plugin id는 `auto-beta-router`) | Auto와 같음 |
| Free Models Router | `openrouter/free` | 필요한 기능(이미지·도구 호출·구조화 출력)을 지원하는 무료 모델 중 무작위 선택 | 문서상 설정 없음 |
| Pareto Router | `openrouter/pareto-code` | Artificial Analysis 코딩 점수로 등급을 나누고 등급 안에서 가장 싼 모델 선택. `:nitro`를 붙이면 p50 처리량이 가장 높은 모델 선택. 같은 등급 예비 모델 2개는 일시 오류나 한도 초과 때만 사용 | `min_coding_score`(0~1, 등급 선택) |
| Fusion Router | `openrouter/fusion` | 여러 모델이 함께 답을 만드는 심층 조사용 | 미확인 |
| 외부 라우터 | `nvidia/switchyard`, `typesafe/jev-router` 등 | 다른 회사가 만든 라우터와 합성 모델 | 미확인 |

**모델 폴백**은 라우터가 아닙니다. 요청에 `models: [A, B, C]`처럼 우선순위 순서로 모델을 적으면 A의 오류(맥락 길이 초과, 검열, 요청 한도, 장애) 때 B를 시도합니다. 고르는 주체는 사용자입니다. 청구는 최종 사용된 모델 기준이며, `:free` 모델에서 유료 모델로 넘어가면 유료 요금이 붙습니다. `sort.partition`의 기본값 `"model"`이면 1순위 모델의 엔드포인트를 먼저 시도합니다.

**실험과의 관계:** 1회 실험([09](09_1회실험_결과.md))는 모델 4개를 고정하고 제공사 선택만 비교해서 라우터를 측정하지 않았습니다. 라우터를 거친 요청도 모델이 정해진 뒤에는 위 제공사 규칙을 따르므로, 모델별 제공사 트래픽에서는 기본 배분이나 필터 사용자 몫에 섞여 있다고 봅니다. 예외는 Pareto Router의 `:nitro`처럼 라우터가 속도 기준으로 고르는 경우입니다.

출처(2026-11-18 확인): [Routers 개요](https://openrouter.ai/docs/guides/routing/routers/overview), [Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router), [Free Models Router](https://openrouter.ai/docs/guides/routing/routers/free-router), [Pareto Router](https://openrouter.ai/docs/guides/routing/routers/pareto-router), [Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks), [`openrouter/auto` 모델 페이지](https://openrouter.ai/openrouter/auto). Auto Code·Fusion·외부 라우터 페이지와 프리셋은 읽지 않았습니다.

### 5-2. 프리셋과 모델 접미사 (2026-11-18 추가)

모델을 정하는 방법은 모델 ID 직접 지정, 모델 폴백, 모델 라우터, 프리셋 네 가지입니다. 공식 문서에서 계정 기본 모델이나 앱 기본 모델 설정은 찾지 못했습니다(앱 기본값은 앱이 모델 ID를 대신 넣는 것으로 봅니다).

- **프리셋:** 모델(단일 또는 폴백 목록), 제공사 선호(정렬·포함·제외), 시스템 프롬프트, 생성 파라미터, 도구를 한 이름으로 저장합니다. `"model": "@preset/이름"`, `"preset": "@preset/이름"`, `"model": "모델@preset/이름"`으로 지정합니다(접두사 없는 이름은 무시). 요청 값과 프리셋 값은 얕게 병합되어 요청 값이 우선하고, API 호출은 항상 최신 버전을 씁니다.
- **모델 자체를 바꾸는 접미사:** `:free`(무료 등급 별도 항목), `:batch`(배치 가격). `:thinking`과 `:extended`는 폐기됨. 해당 항목이 없는 모델에 붙이면 기본 모델로 넘어가지 않고 실패합니다.
- **제공사 정렬만 바꾸는 접미사:** `:nitro`(처리량 정렬, priority 등급 허용), `:floor`(가격 정렬, flex 등급 허용), `:exacto`(도구 호출 신뢰도 신호로 정렬). `:nitro`·`:floor`는 해당 등급 엔드포인트가 쓰이면 기본가와 다른 요금이 붙을 수 있습니다. `:online`은 폐기됨.
- **폴백의 정렬:** `sort.partition` 기본값 `"model"`은 모델별로 묶어 정렬하고, `"none"`은 모든 모델의 엔드포인트를 합쳐 정렬합니다(Provider Selection 문서).

출처(2026-11-18 확인): [Presets](https://openrouter.ai/docs/guides/features/presets), [Model Variants](https://openrouter.ai/docs/guides/routing/model-variants), [Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks), [Provider Selection](https://openrouter.ai/docs/guides/routing/provider-selection). 하위 에이전트가 읽은 요약이므로 중요한 수치를 인용할 때는 원문 재확인이 필요합니다.

## 6. 원문 대조 (2026-11-17)

Traffic Routing, Provider Routing, Prompt Caching 세 문서를 다시 읽고 위 내용과 대조했습니다. 세 페이지 모두 갱신일 표시가 없습니다.

**정정**

- 기본 배분의 몫은 "보정 가격" 하나가 아니라 **보정 가격과 속도의 두 축**으로 정합니다. 2026-11-16판은 속도를 보정 가격의 한 항목처럼 적었습니다. 원문은 속도를 "가격과 맞바꾸는 주된 요인"으로 설명하고, 빠른 엔드포인트는 더 비싸도 트래픽을 받는다고 씁니다. 이 축의 정확한 곡선은 여전히 공개되지 않았습니다.

**그대로 확인**

- 실효 가격(최근 30분, 캐시·입출력 반영)과 예시 $0.142, 오류 1% × 8배 ≈ +8%, 도구 호출 95% ≈ +5%, 429 예시 +$0.01, 오류로 세는 상태 코드 목록
- 차단·단기 후퇴·용량 학습(Provider Routing 문서), 품질 표시 시 탐색 트래픽만, 신규 엔드포인트는 비슷한 제공사 수준에서 시작
- 기본 배분을 건너뛰는 경우: `sort`(계정 기본값 포함), `:floor`·`:nitro`, `order`, 1곳만 남기는 `only`·`ignore`, BYOK. 2곳 이상 남으면 기본 배분
- `:nitro`는 처리량 정렬 + priority 등급, `:floor`는 가격 정렬 + flex 등급을 포함한 상위 집합
- `preferred_min_throughput`·`preferred_max_latency`는 최근 5분 이동 창의 p50·p75·p90·p99로 판단하고, 미달 엔드포인트는 제외하지 않고 뒤로 보냄

**새로 확인 (Prompt Caching 문서의 Provider Sticky Routing)**

| 항목 | 내용 |
|---|---|
| 시작 조건 | 프롬프트 캐시를 쓴 요청 이후, 같은 모델의 후속 요청을 같은 제공사로 보냄. `session_id`가 없으면 **캐시 적중이 감지된 뒤에만** 고착이 시작됨 |
| `session_id` | 요청 본문 `session_id` 또는 `x-session-id` 헤더(최대 256자). 있으면 **첫 성공 요청부터** 고착. 둘 다 없으면 OpenAI 방식 `prompt_cache_key`를 키로 씀 |
| 대화 식별 | 계정·모델·대화 단위. 기본은 첫 시스템(또는 developer) 메시지와 첫 비시스템 메시지의 해시 |
| 유지 시간 | 마지막 성공 요청 후 **60분** 비활성이면 만료. 성공 요청마다 갱신 |
| 예외 | 캐시 읽기 단가가 일반 입력 단가보다 쌀 때만 작동. `provider.order`를 주면 쓰지 않음. 고착 제공사가 오류를 내면 다음 요청은 다시 라우팅 |

**여전히 공개되지 않은 것**

몫 곡선의 수식(가격 역제곱 같은 공식은 없음), TTFT를 가격으로 환산하는 계수, 정렬(`sort`)이 쓰는 지표의 기간·지역, 기본 배분과 사용자 지정의 트래픽 비율.

**실험에 주는 의미**

- 파일럿의 OR-기본 W2에서 24세션 중 20개가 1턴과 2턴을 다른 제공사로 보낸 현상은 "`session_id`가 없으면 캐시 적중 뒤에만 고착" 규칙과 맞습니다. 파일럿 측정 코드는 `session_id`를 기록용으로만 쓰고 API에는 보내지 않았습니다. 2턴 이후에 고착이 바로 걸린 이유(2턴의 평균 캐시 적중률은 15%)는 문서만으로는 설명되지 않습니다.
- 따라서 파일럿에서 본 Mango의 캐시 우위 가운데 2턴 몫은 **클라이언트 설정에 따라 사라질 수 있는 차이**입니다. `session_id`나 `prompt_cache_key`를 보내는 에이전트 클라이언트에서는 OR-기본도 1턴부터 고착됩니다.
