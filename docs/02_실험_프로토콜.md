## 신뢰성 설계 원칙

이 실험은 결과를 의사결정에 그대로 쓸 수 있을 만큼 신뢰할 수 있고, 방법론 자체도 체계적인 기록으로 남도록 설계했습니다. 이를 위해 아래 원칙을 따릅니다.

| 원칙 | 이 문서에서의 구현 |
|---|---|
| 사전 등록 | 질문·지표 정의·판정 기준·제외 규칙·분석 방법을 데이터를 보기 전에 고정 (2~4절, 9절) |
| 측정 대칭 | Mango와 OpenRouter를 같은 측정 코드, 같은 지표 정의, 같은 분해 방법으로 잼 (6~7절) |
| 독립 검증 | OpenRouter 서버 측 기록(Broadcast)과 공개 통계로 우리 측정법을 교차 검증 (7절) |
| 재현성 | 코드·프롬프트·환경·원시 기록을 버전과 해시로 보존. 다른 사람이 같은 절차로 다시 돌릴 수 있게 함 (10절) |
| 불리한 결과도 보고 | 판정 결과가 Mango에 유리하든 불리하든, 가설이 기각되든 같은 형식으로 보고 (12절) |
| 독립성 | Mango를 일반 고객과 같은 조건으로 이용. 제공사가 제공한 수치는 구분 표시 (11절) |
| 한계 명시 | 타당성 위협과 대응, 남는 한계를 결과와 함께 보고 (8절) |
| 비교는 통제된 측정으로만 | 변인을 통제할 수 없는 외부 벤치마크(Artificial Analysis 등)와는 수치를 나란히 놓거나 환산하지 않고 참고로만 봄 (7-3절) |

## 1. 연구 질문

| 번호 | 질문 |
|---|---|
| **RQ1** | 같은 오픈웨이트 모델을 Mango로 직접 부를 때와 OpenRouter로 부를 때(기본 라우팅, 주요 제공사 고정), 사용자가 체감하는 속도·안정성·비용은 어떻게 다른가 |
| **RQ2** | 그 차이 가운데 네트워크·게이트웨이 몫과 서버 처리 몫(prefill·decode)은 각각 얼마인가 |
| **RQ3** | OpenRouter 기본 라우팅은 실제로 어느 제공사에 몇 %를 배분하며, 정렬·단축 경로(`sort`, `:floor`, `:nitro`)에서는 누가 1위인가 |
| **RQ4** | 기본 배분 몫과 공개 30일 점유율의 차이는 사용자 측 선택(직접 지정·정렬·공식 제공사 선호)의 흔적을 보여 주는가 |

## 2. 사전 등록 가설과 판정 기준

**실용적 동등 범위는 ±10%로 정합니다.** 중앙값 비율(Mango ÷ 비교 대상)의 95% 부트스트랩 신뢰구간으로 판정합니다.

| 판정 | 기준 (지연 지표: 작을수록 좋음) |
|---|---|
| Mango 우위 | 신뢰구간 전체가 0.90 미만 |
| Mango 열위 | 신뢰구간 전체가 1.10 초과 |
| 동등 | 신뢰구간 전체가 0.90~1.10 안 |
| 판정 불가 | 위 어디에도 해당하지 않음 (표본 부족 또는 변동 큼) |

처리량처럼 클수록 좋은 지표는 기준을 뒤집습니다(1.10 초과면 우위).

### 주 비교 (1차 결과, 다중 비교 보정 대상)

모델 4개마다 Mango와 **OR-기본**을 비교합니다. 일반 사용자가 받는 성능이 이것이기 때문입니다.

| 번호 | 지표 | 작업 |
|---|---|---|
| P1 | TTFT(content) 중앙값 (서울 체감) | W2 멀티턴 세션의 2턴 이후 (캐시 적중 구간, 실사용과 가장 가까움) |
| P2 | decode 처리량 중앙값 | W1 |
| P3 | 요청 성공률 | 전체 |
| P4 | 성공 세션당 실제 청구 비용 | W2 |

16개 비교(4개 지표 × 4개 모델)에 Bonferroni 보정을 적용합니다(신뢰구간 수준 1 − 0.05/16). 신뢰구간 기반 판정과 바로 맞물리고 계산이 단순해 재현이 쉽기 때문입니다.

### 부 비교·탐색 (보정하지 않고 탐색적 결과로 표시)

- Mango vs OR-고정 제공사 5곳, 작업별·시간대별 차이, p90 꼬리 지연, 도구 호출 성공률.
- 지속 부하 조건(동시성 4)에서의 TTFT·처리량·실패율과 동시성 1 대비 저하 폭.
- 실패 반영 처리량(실패를 0으로 넣은 값)과 작업 동일 비중 종합 대표값.
- RQ2 분해값(네트워크, 고정 지연, prefill 속도, decode 속도).

### RQ3·RQ4 가설

| 번호 | 가설 | 판정 |
|---|---|---|
| H3a | 기본 배분 몫은 보정 가격 순위와 양의 상관을 가진다 (보정 가격이 좋은 제공사가 더 많이 받음) | 모델별 Spearman 상관계수와 신뢰구간. 공식이 비공개라 **탐색적** 판정 |
| H3b | 정렬 경로의 1위는 해당 기준(가격·처리량·지연)의 공개 지표 1위와 일치한다 | 일치율 |
| H4 | 공개 30일 점유율이 기본 배분 몫보다 유의하게 큰 제공사가 있다 (예: Kimi의 Moonshot AI) | 30일 점유율이 기본 배분 몫의 95% 신뢰구간 밖이면 "차이 있음". 이 차이를 사용자 지정 **비율**로 환산하지 않음 |

## 3. 지표 정의

모든 시각은 클라이언트의 단조 증가 시계(`time.perf_counter_ns`)로 잽니다. 요청 송신 직전 시각을 t₀로 둡니다.

| 지표 | 정의 |
|---|---|
| TTFT (any) | 첫 토큰(reasoning 포함)이 담긴 첫 스트리밍 조각의 도착 시각 − t₀ |
| TTFT (content) | 첫 답변 텍스트나 도구 호출이 담긴 조각의 도착 시각 − t₀. reasoning 모델에서는 두 TTFT를 구분해 보고합니다. **주 지표는 content 기준**입니다 |
| E2E 지연 | 마지막 조각 도착 시각 − t₀ |
| decode 처리량 | (출력 토큰 − 1) ÷ (마지막 조각 − 첫 조각). 출력 토큰 수는 조각 개수가 아니라 응답 `usage`의 값을 씁니다 (조각 하나에 여러 토큰이 들어갈 수 있음) |
| ITL | 연속한 조각 도착 간격의 분포. 평균, p50, p90 |
| 전체 처리량 | 출력 토큰(reasoning 포함) ÷ E2E 지연. 첫 토큰 대기를 포함하는 값 |
| 실패 반영 처리량 | 전체 처리량을 집계할 때 엔드포인트 쪽 실패 요청을 0으로 넣은 값. 성공한 요청만 보면 불안정한 곳이 좋아 보이는 문제를 막기 위함 |
| 세션 지표 (W2) | 세션 TTFT = 턴별 TTFT의 평균, 세션 처리량 = 세션 출력 토큰 ÷ 턴별 응답 시간의 합. 도구 결과를 준비하는 시간은 넣지 않음. 세션은 한 턴이라도 실패하면 실패 |
| 성공 | HTTP 200이고, 스트림이 정상 종료되고, 출력이 잘리지 않았으며, W3·W2는 도구 호출 JSON이 스키마에 맞는 경우. 재시도 없이 1회 시도로 판정 |
| 실패 분류 | **엔드포인트 쪽 실패(지표에 포함):** 5xx, 제공사가 보낸 429("Provider returned error" 등), 타임아웃(300초), 스트림 중단, 시간대 마감까지 끝나지 않은 요청. **우리 쪽 실패(제외하고 기록):** 키 오류, 잔액·한도 소진, **OpenRouter 계정 한도 429(`new-account-rpm` 등), Mango 키·조직 한도 429**, 형식 오류나 문맥 길이 초과로 거절된 요청, 측정 코드 오류 |
| reasoning 확인 | 응답마다 reasoning 토큰 수를 기록(`completion_tokens_details.reasoning_tokens` 또는 `usage.reasoning_tokens`, 모델마다 위치가 다름). 켜짐을 지정했는데 0이면 "reasoning 미작동"으로 표시하고 성능 비교에서 구분 |
| 입력 토큰 편차 | 같은 질문에 대한 입력 토큰 수가 엔드포인트마다 다를 수 있음(간이 테스트: DeepSeek 대부분 55~60, `inference-net/us`만 33. GLM-Flash 대부분 40~45, `open-inference/fp4`만 57). 대화 템플릿·계산 방식 차이로 처리량과 청구액이 달라지므로, 모델 중앙값에서 20% 넘게 벗어나면 표시 |
| 조각 크기 | 조각 수 대비 출력 토큰 수. 여러 토큰을 한 조각으로 묶어 보내는 엔드포인트가 있어 ITL은 토큰 기준으로 환산해 해석 |
| 성공 요청당 비용 | 청구 비용 합 ÷ 성공 건수(W2는 성공 세션 수). OpenRouter는 generation 조회의 `total_cost`. **Mango는 응답에 비용이 없으므로** 토큰 수 × `GET /v1/models`의 `cost`(입력·출력·캐시 읽기 단가, 회차마다 스냅샷 저장)로 계산합니다. Mango에는 잔액·사용량 조회 API가 없어(`/v1/usage` 등 404) **콘솔 잔액을 세 시점에 기록**해 대조합니다: 본 실험 시작 직전, 1일차 종료 후, 2일차·품질 점검 종료 후. 구간별 잔액 차이와 계산값 합계의 비율이 1에서 벗어나면 그 비율로 요청별 비용을 보정합니다. 확인은 사용자가 내장 브라우저에 Mango 콘솔을 로그인해 두고, 작성자가 실험 일정이 확정되면 예약 작업으로 걸어 화면을 읽어 기록합니다. 간이 테스트 대조(2026-11-17)에서 콘솔 사용액 $0.03이 할인 전 단가 계산값 $0.028~0.032와 일치해, 현재 청구는 할인 전 가격 기준입니다 |
| 네트워크 RTT | TCP 연결 시간(연결 수립에 걸린 시간). TLS 핸드셰이크는 별도 기록 |

**연결 재사용 규칙.** 연결 수립 시간이 TTFT에 섞이지 않도록 arm마다 연결을 미리 열어 두고 재사용합니다(keep-alive). 연결 단계 시간은 시간대마다 새 연결을 따로 열어 측정합니다.

## 4. 대상과 환경

### 모델과 비교군

모델은 가격 비교 데이터([data](../data/openrouter_mango_listed_compare_20261116.csv))와 같은 4개입니다. Mango의 호출 가능 목록은 키별로 다르므로 실행 전에 `GET /v1/models`로 모델 ID를 확인합니다.

| 모델 (Mango ID · 양자화) | OpenRouter 30일 토큰 | OR-고정 대상: 점유율 상위 5개 제공사의 대표 엔드포인트 (양자화) |
|---|---:|---|
| Kimi K3.1 Pro (`moonshotai/Kimi-K3.1-Pro` · mxfp4) | 10.75T | `moonshotai/mxfp4` (mxfp4), `inference-net/mxfp4` (mxfp4), `modal/mxfp4` (mxfp4), `wafer/us` (mxfp4), `together` (미표기) |
| GLM-5.3-Flash (`zai-org/GLM-5.3-Flash` · fp8) | 56.32T | `together` (미표기), `inference-net/us` (fp4), `open-inference/fp4` (fp4), `coreweave/nvfp4` (nvfp4), `z-ai/fp8` (fp8) |
| GLM-5.3 (`zai-org/GLM-5.3` · mxfp4) | 17.84T | `wafer/us` (fp4), `inference-net/us` (fp4), `z-ai/fp8` (fp8), `siliconflow/fp8` (fp8), `decart/fp4` (fp4) |
| DeepSeek V4.1 Flash 1017 (`deepseek-ai/DeepSeek-V4.1-Flash-1017` · fp4) | 200.66T | `deepseek` (미표기), `deepinfra/fp8` (fp8), `together` (미표기), `inference-net/us` (fp8), `wafer/us` (mxfp4) |

**대표 엔드포인트 규칙.** 같은 제공사라도 엔드포인트마다 양자화·가격·지역이 다르므로(예: Kimi `wafer/us` 입력 $0.25 vs `wafer/mxfp4` $1.80) 제공사가 아니라 엔드포인트로 고정합니다. 제공사마다 fast·flex·priority·prime 등급을 뺀 표준 엔드포인트 중 가격 표본 토큰이 가장 많은 것을 고릅니다(가격 비교 데이터([data](../data/openrouter_mango_listed_compare_20261116.csv))와 같은 규칙, [비교 CSV](../data/openrouter_mango_listed_compare_20261116.csv)의 `endpoint` 열). OpenRouter는 엔드포인트별 사용량을 공개하지 않으므로(사용량은 제공사 단위만 공개) 가격 표본 토큰을 사용량의 대리 지표로 씁니다. 실제 사용량 순위와 다를 수 있다는 한계가 있습니다. 2026-11-16 공개 통계로 확인한 결과 20개 고정 엔드포인트가 모두 각 제공사 안에서 가격 표본 토큰 1위였습니다([엔드포인트 통계 CSV](../data/openrouter_endpoint_stats_20261116.csv)의 `rank_within_provider`). Mango 양자화는 `GET /v1/models`의 `quantization`(Mango 자체 표기), OpenRouter는 엔드포인트 정보 기준입니다. **양자화는 맞추지 않고 기록합니다.** 양자화는 제공사의 사업 선택이고 주 비교는 사용자가 받는 성능이기 때문입니다.

| arm | 호출 방식 | 실험 |
|---|---|---|
| M | Mango `/v1/chat/completions` 직접 | A |
| OR-기본 | OpenRouter, provider 설정 없음 | A + B |
| OR-고정 ×5 | `provider: {order: ["엔드포인트 슬러그"], allow_fallbacks: false}` (예: `wafer/us`) | A |
| B-price / throughput / latency | `provider: {sort: …}` | B |
| B-floor / B-nitro | `모델:floor`, `모델:nitro` | B |

### 공통 요청 조건

- 스트리밍 켬. 클라이언트는 OpenAI 공식 Python SDK를 쓰고, 연결 단계 시간을 재기 위해 이벤트 훅을 단 `httpx` 클라이언트를 SDK에 넣습니다. 실제 개발자가 쓰는 라이브러리와 같은 조건으로 부르기 위함입니다.
- **샘플링 설정은 모델 제작사 권장값을 따르고, 모든 arm에 같은 값을 명시합니다**(2026-11-17 Hugging Face 모델 카드 확인).

  | 모델 | temperature | top_p | 근거 |
  |---|---:|---:|---|
  | DeepSeek V4.1 Flash 1017 | 1.0 | 1.0 | 모델 카드 "Recommended sampling parameters" ([deepseek-ai/DeepSeek-V4.1-Flash-1017](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)) |
  | GLM-5.3 | 1.0 | 0.95 | `generation_config.json` 기본값, 평가 설정 ([zai-org/GLM-5.3](https://huggingface.co/zai-org/GLM-5.3)) |
  | GLM-5.3-Flash | 1.0 | 0.95 | `generation_config.json` 기본값 ([zai-org/GLM-5.3-Flash](https://huggingface.co/zai-org/GLM-5.3-Flash)) |
  | Kimi K3.1 Pro | 1.0 | 0.95 | 모델 카드의 평가 설정 "temperature = 1.0, top-p = 0.95" ([moonshotai/Kimi-K3.1-Pro](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)) |

  Mango의 DeepSeek·GLM-5.3은 `GET /v1/models`의 지원 파라미터 목록에 `top_p`가 없습니다. 보내도 무시될 수 있으며, 그 경우 서버 기본값(GLM-5.3은 `generation_config` 기준 0.95로 추정, DeepSeek은 1.0)이 적용됩니다. 엔드포인트별 지원 파라미터 목록을 기록해 해석에 씁니다.
- **`max_tokens`는 답변이 잘리지 않을 만큼 크게 둡니다.** reasoning 모델은 답변 전에 추론 토큰을 쓰기 때문에, 작은 상한을 주면 답변이 나오기 전에 잘립니다. 엔드포인트 출력 한도까지, 상한 32,768로 두고 파일럿에서 잘림 비율을 확인합니다(잘림이 1%를 넘으면 상한을 올림).
- **reasoning은 "켜짐"으로 통제합니다.** [reasoning 설정 시험](04_reasoning설정_시험.md)에서 모든 모델·엔드포인트의 기본값이 켜짐이었고, GLM-5.3·GLM-5.3-Flash는 끌 수 없었습니다(OpenRouter 400 "Reasoning is mandatory"). 그래서 OpenRouter 경로에는 `reasoning: {"enabled": true}`를 명시합니다. Mango는 공식 조절 파라미터가 없고 기본값이 켜짐이므로 아무것도 보내지 않습니다(문서에 없는 `chat_template_kwargs`는 GLM-5.3에서 오작동). 실제로 켜졌는지는 응답의 reasoning 토큰 수로 확인합니다(3절). 강도 조절(`effort`)은 일부 모델·엔드포인트에서 작동하지만, 모든 곳의 기본값이 켜짐이고 기본값으로 쓰는 사용자가 다수이므로 "줄임" 같은 보조 조건은 두지 않습니다.
- SDK 자동 재시도는 끕니다(`max_retries=0`). 실패한 요청은 다시 보내지 않고 실패로 기록합니다.
- Mango 스트리밍 응답에 usage가 없으면 `stream_options: {include_usage: true}`를 붙입니다. OpenRouter는 usage를 자동으로 반환합니다([usage accounting](https://openrouter.ai/docs/use-cases/usage-accounting)).
- 모든 요청에 고유 요청 ID를 붙입니다. OpenRouter에는 요청 본문 `trace.trace_id`로 넣어 서버 측 기록과 결합합니다([Broadcast](https://openrouter.ai/docs/guides/features/broadcast)).

### 실행 환경: 클라우드 VM

측정은 클라우드 VM에서만 합니다. 사용자 PC는 쓰지 않습니다. 데이터센터 회선이라 반복 측정이 일관되고, 정시 실행과 재현이 쉽고, 공인 주소가 있어 Broadcast 원본을 직접 받을 수 있기 때문입니다.

| 측정 지점 | 범위 | 역할 |
|---|---|---|
| **서울 리전 VM** | 프로토콜 전체 (실험 A·B, RQ2, Q) | 주 측정. 1차 판정의 유일한 근거 |
| 미국 동부 리전 VM (선택) | 축소판: M과 OR-기본 × W1·W2 × 시간대 4개 (서울과 같은 회차 수), 연결 단계 측정 | 지리 효과 확인. 서울 파일럿 후 예산을 보고 실행 여부 결정. 결과는 탐색적 결과로만 보고 |

| 항목 | 설정 |
|---|---|
| VM 사양 | 소형 범용 인스턴스 (2 vCPU, 메모리 4GB 수준), Ubuntu LTS. 두 지역 같은 사양 |
| 소프트웨어 | Python 3.12 가상환경, 라이브러리 버전 고정 목록(lock 파일) |

| Broadcast 수신 | 서울 VM에 가벼운 Webhook 수신기를 띄워 원본 JSON을 파일로 저장. OpenRouter가 HTTPS 주소를 요구하는지는 파일럿 전에 확인. 요구하면 도메인 + 자동 TLS(예: Caddy)를 붙이거나, 수신처를 S3 또는 Langfuse로 바꿈 |

## 5. 실험 설계

### 5-1. 작업 (workload)

OpenRouter 실사용은 입력 97~99%, 캐시 적중 84~94%입니다(가격 비교 데이터([data](../data/openrouter_mango_listed_compare_20261116.csv))). 짧은 채팅만 재면 실사용과 동떨어지므로 아래 작업을 둡니다.

출력 상한은 4절 공통 요청 조건대로 답변이 잘리지 않을 만큼 크게 둡니다(L·Z만 예외).

| 작업 | 입력 | 측정 목적 |
|---|---|---|
| W1 단일 요청 | 약 1k 토큰. 프롬프트 풀에서 뽑음 | 기본 TTFT, decode 처리량 (P2) |
| W2 멀티턴 에이전트 세션 | 약 16k 토큰 시스템·코드 문맥으로 시작해 10턴. 매 턴마다 도구 호출과 도구 결과(1~2k 토큰)가 붙어 문맥이 약 30k까지 늘어남 | 캐시 적중 TTFT (P1), 세션 비용 (P4), 도구 호출 성공 |
| W3 도구 호출 단일 요청 | 약 2k 토큰 + 도구 3개 정의 | 도구 호출 성공률, 실험 B의 두 번째 요청 크기 |
| L 입력 길이 단계 | 1k / 10k / 32k 토큰, 캐시 없이, 출력 상한 16 | prefill 속도와 고정 지연 분해 (RQ2) |
| Z 최소 요청 | 수십 토큰, 출력 상한 1 | 순수 오버헤드 (RQ2) |
| Q 품질 점검 | 정답이 정해진 문항 400개: 어려운 수학 풀이 200(MATH 상위 난이도), 전문 지식 객관식 150(MMLU-Pro), 도구 호출 정확도 50(BFCL). 출처·라이선스는 문항 생성 시 확인해 기록 | 양자화·구현 차이로 품질이 떨어지는지 확인. 같은 문항을 모든 경로에 내는 짝지은 비교로 약 5~6%p 차이까지 구분 |

**프롬프트 풀.** 출력 종류에 따라 생성 속도가 달라집니다(추측 디코딩처럼 출력 패턴을 활용하는 기법 때문). 그래서 W1·W3 프롬프트는 한 종류로 두지 않고 코드 작성, 설명문, 요약, JSON 추출, 수학 풀이를 고르게 섞은 풀(각 W1·W3 200개 이상)에서 뽑습니다.

**W2 세션은 고정 대화 기록으로 진행합니다.** 각 턴의 이전 기록(사용자 지시, 모델 응답, 도구 결과)을 미리 만들어 둔 고정 텍스트로 보냅니다. 모델이 실제로 낸 응답은 측정만 하고 다음 턴 입력에 넣지 않습니다. 그래야 모든 arm이 턴마다 **글자 하나 다르지 않은 같은 입력**을 받아 비교가 공정해집니다. 접두부가 턴마다 그대로 이어지므로 캐시는 실사용처럼 적중합니다. 도구 결과는 고정 텍스트라 도구 실행 시간이 없습니다.

프롬프트 세트는 기밀이 아닌 공개 텍스트로 만들고 `code/`에 보관합니다. 세트 파일의 SHA-256을 기록합니다.

### 5-2. 캐시 고착 차단과 무작위화

- **같은 프롬프트를 모든 arm에 (짝지은 설계):** 회차마다 프롬프트 풀에서 뽑은 같은 프롬프트 묶음을 모든 arm에 보냅니다. arm 간 차이가 프롬프트 차이 때문에 생기지 않고, 같은 프롬프트끼리 짝지어 비교할 수 있어 적은 표본으로도 차이를 더 정확히 잡습니다.
- **nonce:** 모든 요청의 **첫 메시지를 nonce만 담은 시스템 메시지**(`ID: <16자리 16진수>`)로 시작합니다(W2는 기존 시스템 메시지 맨 앞에 붙임). 사용자 메시지 앞에만 붙이면, 시스템 메시지가 없을 때 대화 템플릿이 자동으로 넣는 기본 시스템 문구가 nonce보다 앞에 와서 그 부분은 요청끼리 캐시됩니다. 간이 테스트·reasoning 시험에서 Kimi K3.1 Pro가 이렇게 호출당 약 36토큰씩 캐시 적중했습니다(Mango 대시보드의 캐시 입력 320토큰과 기록이 정확히 일치). 무작위 문자열은 W1·W3·L·Z·Q는 요청마다, W2는 세션마다 새로 붙입니다. 그래서 세션 안에서는 캐시가 적중하고, 세션 사이·arm 사이·시간대 사이에는 캐시가 섞이지 않습니다. 같은 프롬프트를 여러 arm에 보내도 nonce가 달라 서로의 캐시를 쓰지 못합니다.
- **arm 순서:** 회차마다 무작위로 섞습니다. 시간에 따른 부하 변화가 특정 arm에 몰리지 않게 하기 위함입니다. 난수 시드를 기록합니다.

### 5-3. 통합 실행 루프

실험 A의 OR-기본 호출은 응답 제공사가 기록되므로 그 자체로 실험 B의 기본 배분 표본입니다. 두 실험을 같은 시간대 루프에서 한 번에 실행합니다.

| 항목 | 방식 |
|---|---|
| 공유 호출 | OR-기본 호출 한 번으로 RQ1의 "기본 경로 성능"과 RQ3의 "기본 배분 몫"을 동시에 얻음 |
| OR-기본 표본 | W1·W3는 시간대당 75회(다른 arm은 15회) |
| W2 이중 활용 | 세션 1턴은 캐시 없는 긴 요청 배분 표본(참고용), 2~10턴은 같은 제공사에 머무는지 보는 고착 관측 |
| B 요청 크기 | W1(짧음)·W3(도구 호출)를 그대로 사용 |

**시간대는 6시간 간격 4회입니다.** KST 03·09·15·21시(UTC 18·00·06·12시)로 하루를 고르게 덮어, 미국·유럽·아시아 업무 시간대의 부하가 모두 들어가게 합니다. 회차당 횟수를 줄여 하루 셀당 표본 수는 이전 설계(3회 × 20회 = 60)와 같게 유지합니다.

**시간대 1회 실행량 (1일차).**

| 구분 | 모델 1개당 | 4개 모델 |
|---|---:|---:|
| A: M + OR-고정 5 = 6 arm × (W1 15 + W3 15 + W2 2세션 × 10턴) | 300 | 1,200 |
| A+B: OR-기본 (W1 75 + W3 75 + W2 2세션 × 10턴) | 170 | 680 |
| B: 정렬·단축 arm 5개 × 2 크기 × 8회 | 80 | 320 |
| RQ2: L 7 arm × 3 길이 × 4회 | 84 | 336 |
| RQ2: Z 7 arm × 8회 | 56 | 224 |
| 부하 조건: M·OR-기본 × W1 × 동시성 4로 6묶음(24건) | 48 | 192 |
| 합계 | 738 | **2,952** |

| 일정 | 내용 | 건수 |
|---|---|---:|
| 0일차 | 파일럿 (경로 × 작업별 5회) | 약 1,100 |
| 품질 점검 회차 (1회) | Q 400문항 × 6 arm(M + OR-고정 5) × 4 모델. 본 회차와 겹치지 않는 시간에 따로 실행 | 9,600 |
| 1일차 | 시간대 4개 × 통합 루프 | 11,808 |
| 2일차 | 시간대 4개 × B만 반복 (OR-기본 W1·W3 + 정렬·단축 arm) | 3,680 |
| 서울 합계 | | **약 26,200** (본 측정 약 16,600 + 품질 점검 9,600) |
| (선택) 미국 축소판 | 1일차와 같은 시간대 4개 × (M·OR-기본 × (W1 15 + W2 20) × 4 모델) | 1,120 |

모든 건수는 서울 VM 기준입니다.

**실행 방식.** 모델 × arm 조합마다 독립된 작업자를 두고, 작업자 안에서는 동시성 1로 순차 호출합니다. 동시 스트림은 16개 이하로 제한합니다(한 프로세스에서 스트림이 너무 많으면 측정 시각이 밀림). **부하 조건은 본 루프가 끝난 뒤 따로** 돌립니다. 우리 VM이 만드는 부하가 다른 arm 측정에 섞이지 않게 하기 위함입니다. **Mango 호출 한도:** Mango 기본 등급(누적 지출 $0)은 키당 분당 40회·동시 4건, 누적 $50 이상이면 분당 150회·동시 16건입니다([Rate limits](https://inference.mangoboost.io/docs/operations/rate-limits/)). 등급과 관계없이 재현성을 위해 기본 등급 기준으로 고정합니다. 본 루프의 Mango 호출은 모델 4개를 합쳐 동시 3건·분당 36회 이하로 묶고, 부하 조건만 동시 4건으로 실행합니다(그때 다른 Mango 호출 없음). Mango 한도 429도 우리 쪽 실패로 분류합니다. 실행 시점의 Mango 등급을 기록합니다. **OpenRouter 계정 한도:** 새 계정은 모델당 분당 20회로 제한됩니다(Kimi K3.1 Pro에서 확인). 모델별 OpenRouter 호출은 분당 18회 이하로 묶고, 이 한도에 걸린 429는 우리 쪽 실패로 분류해 같은 회차 끝에 다시 보냅니다. 한도가 풀리는 조건은 파일럿 전에 확인합니다. 시간대당 1시간 30분 안팎을 목표로 하고, 파일럿에서 실제 소요 시간을 확인합니다. reasoning 출력이 길어 시간이 넘치면 회차당 횟수를 줄이고 회차를 늘립니다(이탈 기록에 남김).

## 6. 측정 체계

### 6-1. 구성

```
측정 코드 (서울 리전 VM, 조각별 시각·연결 단계 기록)
  ├─▶ Mango /v1 ───────────────────────────────┐
  │     └─ 응답 헤더·usage 전체 저장            ├─▶ ① 원시 JSONL (요청 ID 기준)
  └─▶ OpenRouter (trace_id = 요청 ID) ──────────┘
          ├─▶ ③ Broadcast ─▶ 서울 VM의 Webhook 수신기 (원본 JSON)  [+ 선택: Langfuse 화면]
          └─▶ ② 실행 후 generation 조회 (제공사, 폴백 내역, 비용, 캐시 토큰)

집계: 요청 ID로 ①②③ 결합 → 검증 → 07_데이터 CSV
```

**측정 코드는 직접 작성합니다.** 성능 지표는 어떤 도구를 쓰든 클라이언트가 조각을 받는 시각으로 계산하므로, 직접 측정한 값의 정확도는 도구와 같습니다. 그리고 이 실험에는 범용 도구가 채우지 못하는 요구가 있습니다. arm 혼합, `provider` 객체, 응답 제공사 기록, W2 세션 단위 nonce가 그렇습니다. **프록시 방식 도구는 쓰지 않습니다.** 네트워크 구간이 하나 늘어 지연이 왜곡되기 때문입니다(Langfuse 게이트웨이 기능 포함).

### 6-2. 계층별 역할

| 계층 | 수단 | 얻는 것 | 대칭성 |
|---|---|---|---|
| ① 원본 | 직접 작성한 Python 측정 코드 (OpenAI 공식 SDK 비동기 스트리밍 + 연결 단계 이벤트 훅을 단 `httpx` 클라이언트) | 조각별 도착 시각, TTFT, ITL, E2E, 연결 단계(TCP·TLS) 시간, 응답 헤더·본문 전체 | **양쪽 동일. 모든 1차 결과의 근거** |
| ② OpenRouter 서버 기록 | [generation 조회 API](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation.md) | `provider_name`, `provider_responses[]`(폴백 시도 내역), `latency`·`generation_time`(ms), 원본·캐시·reasoning 토큰, `total_cost`, `service_tier` | OpenRouter만. RQ3 제공사 식별의 근거 |
| ③ OpenRouter 구간 분해 | [Broadcast](https://openrouter.ai/docs/guides/features/broadcast) | `router_ms`, `provider_ms`, `provider_failed_ms`, `attempt_count`, 제공사 기준 TTFT·토큰 간 간격 | OpenRouter만. **7절 측정법 검증용** |
| ④ Mango 보조 | 응답 헤더·usage, 콘솔 사용량 분석 화면 | 캐시 토큰, 서버 처리 시간 헤더 등 제공되는 것 (무엇이 오는지는 파일럿에서 확인) | Mango만. 제공사 측 값으로 구분 표시 |
| ⑤ 보기·공유 (선택) | Langfuse (Broadcast 수신처 겸 열람 화면) | 요청 기록 열람, 지연 백분위 대시보드 | 측정에는 쓰지 않음 |
| ⑥ 교차 검증 (선택) | [GuideLLM](https://github.com/vllm-project/guidellm) | Mango 동시성·부하 단계 처리량을 ①과 대조 | 같은 프롬프트로 양쪽 가능 |

**Broadcast 수신처는 서울 VM의 Webhook 수신기를 원본으로 씁니다.** 원본 JSON이 그대로 쌓여 ① 기록과 결합하기 가장 단순합니다. HTTPS 요구 등으로 직접 수신이 어려우면 S3로 바꿉니다(4절 실행 환경). Langfuse는 팀 공유용 화면이 필요할 때만 덧붙입니다. Broadcast의 구간별 시간 값이 Langfuse에서 어떤 필드로 보이는지는 파일럿에서 확인합니다.

## 7. 대칭 분해와 검증 (RQ2)

Mango에는 OpenRouter의 Broadcast 같은 서버 측 구간 기록이 없고, Mango는 OpenRouter 제공사가 아니라서 같은 경로로 부를 수도 없습니다. 그래서 **양쪽에 똑같이 적용할 수 있는 클라이언트 측 분해법**을 쓰고, Broadcast는 그 분해법을 검증하는 데만 씁니다.

### 7-1. 분해 방법 (양쪽 동일)

| 구간 | 방법 |
|---|---|
| 네트워크 | 새 연결의 TCP 연결 시간 ≈ RTT. 시간대마다 arm별로 10회 측정 |
| 고정 지연 + prefill 속도 | L 작업에서 `TTFT = a + b × 입력 토큰` 회귀. **b = prefill 속도의 역수**, **a = 고정 지연**(네트워크 + 게이트웨이 + 대기열) |
| 서버 쪽 고정 지연 | a − RTT. OpenRouter는 게이트웨이를 포함 |
| 최소 오버헤드 | Z 작업의 TTFT 분포 (회귀 절편 a와 대조) |
| decode 속도 | W1의 ITL과 decode 처리량. 네트워크는 흔들림만 더하고 평균은 거의 바꾸지 않음 |
| 캐시 효과 | W2 세션 1턴과 2~10턴의 TTFT 차이 (입력 길이 증가분은 L 회귀로 보정) |

### 7-2. 측정법 검증 (보정)

1. **OpenRouter에서 맞춰 보기:** OR-고정 arm마다 7-1로 추정한 "서버 쪽 고정 지연"을 Broadcast의 `router_ms`, 제공사 기준 TTFT와 비교합니다.
2. **판정:** 추정값과 Broadcast 값의 차이가 중앙값 기준 ±20% 안이면 분해법이 타당하다고 보고, 같은 방법으로 낸 Mango 분해값을 결과로 씁니다. 범위를 벗어나면 Mango 분해값은 "검증되지 않은 추정"으로 표시합니다.
3. **공개 통계와 맞춰 보기:** OR-고정 측정값(TTFT·처리량)을 **같은 엔드포인트**의 OpenRouter 공개 1주 통계([엔드포인트 통계 CSV](../data/openrouter_endpoint_stats_20261116.csv), 본 실행 시점에 다시 수집)와 비교합니다. 월간 제공사 통계([data](../data/openrouter_monthly_share_final_20261116.csv))의 제공사 값은 여러 엔드포인트의 가중평균이라 이 비교에 쓰지 않습니다(예: Kimi Moonshot의 29 tok/s에는 `moonshotai/mxfp4` 28과 `moonshotai/highspeed` 54.5가 섞여 있음). 순위가 같은 방향인지(Spearman 상관) 확인합니다. 다를 경우 측정 위치(서울)와 측정 시점 차이로 설명되는지 검토합니다.
4. **품질 점검:** 같은 문항에 대한 Mango와 각 고정 엔드포인트의 정답 여부를 짝지어 비교합니다(McNemar 검정, 차이의 95% 구간). 같은 모델 안에서 정답률이 6경로 중앙값보다 10%p 이상 낮은 경로는 성능 결과에 표시합니다. 4비트 계열(fp4·mxfp4·nvfp4)과 8비트(fp8)의 정답률 차이를 탐색적으로 보고합니다. 양자화는 신고 값 기준입니다.

### 7-3. 외부 벤치마크는 참고로만

Artificial Analysis(이하 AA)는 제공사 성능을 6시간마다 측정해 온 독립 벤치마크입니다. 방법론을 검토한 결과([정리](06_참고_ArtificialAnalysis_방법론.md)), 결과를 크게 좌우하는 동시 부하 수준, 프롬프트 세트, 멀티턴 작업 내용이 공개되지 않아 같은 조건을 만들 수 없습니다. 그래서 다음 규칙을 둡니다.

- **모든 비교는 이 프로토콜의 통제된 측정으로만 합니다.** AA 수치와 우리 수치를 같은 표에 나란히 놓거나, 한쪽을 다른 쪽 기준으로 환산하지 않습니다.
- AA는 보고서의 별도 "참고" 절에서만 다룹니다. 쓰는 내용은 다음으로 한정합니다.
  - 지표 정의·실패 처리 규칙이 업계에서 어떻게 쓰이는지 (우리 정의 점검용)
  - 같은 제공사들 사이 순위가 대체로 같은 방향인지에 대한 정성적 언급
  - Mango의 AA 등재 여부
**대신 방법은 배워 왔습니다.** 수치는 섞지 않지만, 오래 운영된 측정 방식에서 검증된 관행은 이 프로토콜에 반영했습니다.

| AA에서 배운 것 | 이 프로토콜에 반영한 방식 | 위치 |
|---|---|---|
| 출력 종류에 따라 속도가 달라지므로 다양한 프롬프트를 쓰고, 같은 프롬프트를 모든 엔드포인트에 보냄 | 출력 종류를 섞은 프롬프트 풀, 회차마다 같은 프롬프트를 모든 arm에 (짝지은 설계) | 5-1, 5-2 |
| 멀티턴 에이전트 작업(도구 호출 포함)을 정식 작업으로 측정, 도구 실행 시간은 제외, 세션 단위 지표 | W2를 고정 대화 기록 기반 10턴 세션으로 변경 | 3, 5-1 |
| 1k·10k·100k 입력 단계 | 입력 길이 단계 1k·10k·32k (비용 때문에 100k 제외) | 5-1 |
| reasoning 모델은 제작사 권장 샘플링, max_tokens를 크게 | 제작사 권장값, 출력 상한 32,768로 잘림 방지 | 4 |
| 실제 운영을 반영해 동시 부하에서 측정 | 동시성 1(주)과 동시성 4(부 비교)를 함께 측정. Mango 기본 등급의 키당 동시 한도가 4라 그 이상은 우리 쪽 429가 섞임 | 2, 5-3 |
| 엔드포인트 쪽 실패는 처리량 0으로 계산, 우리 쪽 실패는 제외, 마감까지 안 끝난 요청은 실패 | 실패 분류와 실패 반영 처리량 | 3 |
| 회차별 중앙값 → 회차 평균, 작업 동일 비중 대표값 | 계층 집계, 종합 대표값(보조) | 9 |
| 일정 간격의 반복 측정 | 6시간 간격 4회 | 5-3 |
| 출력 토큰 수는 제공사 API 보고값 | 동일 (조각 개수로 세지 않음) | 3 |
| OpenAI 호환 제공사는 OpenAI 공식 Python 라이브러리 | 동일 | 4 |
| 별도 익명 계정으로 조작 여부 검증 | 두 번째 Mango 계정 교차 측정(선택) | 11 |

따르지 않은 것: 측정 위치(미국 중부 한 곳 → 우리는 서울), 5일 평균(우리는 이틀), 공개되지 않은 동시 부하 수준(우리는 8로 정하고 명시).

- 7-2절 검증에 쓰는 외부 자료는 OpenRouter 공개 통계와 Broadcast뿐입니다. 이 둘은 같은 제공사·같은 경로를 다루는 자료라서 쓸 수 있습니다. 그래도 순위의 방향만 확인하고 수치를 섞지는 않습니다.

## 8. 타당성 위협과 대응

| 위협 | 대응 | 남는 한계 |
|---|---|---|
| 지리: Mango는 서울 데이터센터, OpenRouter 제공사는 대부분 해외 | RTT로 네트워크 몫을 분리하고 결과를 두 가지로 보고: ① 서울 기준 체감값, ② 네트워크를 뺀 서버 성능. 선택 시 미국 VM 축소판으로 위치 효과 확인 | 서울 결과는 Mango에 가장 유리한 위치의 값. 미국 축소판을 하지 않으면 해외 고객 관점은 ②로만 추정 |
| 측정 지점 대표성: 데이터센터 회선 | 클라우드 VM에서 부르는 서비스·앱 기업(B2B)과 같은 조건. 가정·사무실 회선은 측정하지 않음 | 개발자 PC에서 직접 부르는 코딩 에이전트 사용자의 체감과는 다를 수 있음 |
| 클라우드 사업자 편향 | ASN·경로 확인 후 Mango와 같은 사업자면 교체 (4절) | - |
| 게이트웨이: OpenRouter에만 있음 | 실제 사용자가 겪는 차이라 그대로 둠. Broadcast로 게이트웨이 몫을 측정해, Mango가 OpenRouter에 입점하는 경우를 "Mango 서버 성능 + 게이트웨이 몫"으로 따로 계산 | 입점 시 실제 라우팅 몫은 알 수 없음 |
| 시간대 부하 변동 | 6시간 간격 4회 × 이틀, arm 순서 무작위화 | 2일 측정이 평소를 대표하는지는 미지수 (참고로 AA는 5일 평균) |
| 프롬프트 차이 | 모든 arm에 같은 프롬프트(짝지은 설계), 출력 종류를 섞은 프롬프트 풀 | 풀 구성이 실사용 분포와 다를 수 있음 |
| 이상적 조건 편향 | 동시성 1 외에 지속 부하(동시성 4) 조건을 부 비교로 측정 | 실제 운영 부하는 우리 한 계정으로 재현할 수 없음 |
| 캐시 | 첫 시스템 메시지에 nonce를 넣어 차단, W2는 세션 안에서만 적중. 캐시 토큰 수를 usage로 확인하고, W2 외 요청에서 캐시가 입력의 5%를 넘으면 표시 | 대화 템플릿의 선두 토큰 몇 개(역할 표시 등)는 nonce보다 앞이라 캐시될 수 있음. Mango GLM-5.3은 캐시 토큰을 보고하지 않아 간접 추정 |
| 출력 길이·reasoning 차이 | 토큰 기준 정규화, reasoning 설정 명시, reasoning 토큰 별도 기록 | 같은 설정에서도 구현마다 reasoning 길이가 다를 수 있음 |
| 양자화·모델 차이 | 양자화는 맞추지 않고 신고 값을 회차마다 기록(Mango `GET /v1/models`, OpenRouter 엔드포인트 정보). Q 품질 점검 400문항으로 결과를 확인. 모델 버전(OpenRouter permaslug, Mango `weight_version`) 기록 | 신고 값은 검증 불가 |
| 측정 코드 오류 | 파일럿 합격 기준(11절), GuideLLM 교차 검증, Broadcast와 대조 | - |
| 클라이언트 측 지연 | 동시 스트림 16개 이하. 파일럿에서 동시 1개와 16개의 TTFT 차이를 측정해 영향이 2% 미만인지 확인 | - |
| 로컬 회선 장애 | 1분마다 양쪽 호스트 연결 시간을 대조군으로 측정. 로컬 장애 구간은 9절 규칙으로 처리 | - |
| 평가 계정 우대 | 11절 독립성 규칙 | 우대 여부를 완전히 배제할 수는 없음 |

## 9. 분석 계획

| 항목 | 방법 |
|---|---|
| 요약 통계 | 지표별 p50, p90, p99. 평균은 보조 |
| 계층 집계 | 시간대(회차)마다 셀별 중앙값을 구하고, 대표값은 회차 중앙값들의 평균. 한 회차의 부하 이상이 전체를 좌우하지 않게 하기 위함 |
| 종합 대표값 (보조) | 작업별 대표값을 같은 비중으로 평균한 값. 주 판정에는 쓰지 않음 |
| 짝지은 비교 | 같은 프롬프트에 대한 arm 간 비율(로그 차이)로 비교해 프롬프트 간 변동을 제거 |
| 신뢰구간 | 부트스트랩 10,000회, 95%. 시간대를 층으로, 프롬프트를 단위로 재표본 |
| 주 비교 판정 | 2절 기준. 16개 주 비교에 Bonferroni 보정 (99.6875% 구간) |
| 비율 지표 | 성공률·배분 몫은 Wilson 95% 신뢰구간 |
| RQ3 배분 몫 | **엔드포인트 단위와 제공사 단위로 각각 집계.** 첫 시도 기준과 최종 기준(`provider_responses[]`) 두 가지. 시간대·요청 크기별 비교. 엔드포인트 단위 배분은 OpenRouter가 공개하지 않는 정보라 별도 결과로 보고 |
| RQ3 역추적 점검 | 같은 회차의 공개 엔드포인트 지표(`/api/v1/models/{author}/{slug}/endpoints`)로 보정 가격 순위를 매기고 배분 몫과 Spearman 상관 |
| RQ4 | 2절 H4 기준. **30일 점유율이 제공사 단위로만 공개되므로, 기본 배분 몫을 제공사로 합쳐서 비교**. 측정 기간(이틀 vs 30일), 계정 1개, BYOK 포함 여부 미확인을 함께 표시 |
| 결측·실패 | 제공사 측 오류·타임아웃은 **제외하지 않고** 실패로 집계 |

**사전 정의 제외 규칙 (이 경우에만 제외).**
1. 측정 코드 오류로 기록이 깨진 요청 (로그로 원인을 확인한 경우).
2. 대조군 연결 시간이 해당 시간대 중앙값의 3배를 넘는 로컬 장애 구간의 요청. 이 경우 해당 구간 전체를 제외하고 같은 시간대에 재측정합니다.
3. 파일럿 요청 (본 분석에 섞지 않음).

제외 건수와 사유는 결과 보고서에 모두 적습니다.

## 11. 품질 관리와 독립성

### 파일럿 합격 기준 (모두 충족해야 v1.0으로 동결)

- 모든 arm × 모델에서 5회 이상 성공하고, 필수 필드 결측이 0건.
- OpenRouter 요청 전부가 generation 조회와 Broadcast에 결합됨 (결합률 99% 이상).
- 측정 코드의 출력 토큰 수와 서버 usage가 일치. 청구 비용 합이 계정 청구 내역과 ±2% 안에서 일치.
- 동시 1개 vs 16개 TTFT 차이 2% 미만. Broadcast 켬·끔의 TTFT 차이 2% 미만.
- 실측 비용으로 15절 예산을 다시 계산.

### 실행 중 점검과 중단 기준

- 시간대마다 실패율, 결측, 결합률을 자동 점검합니다.
- 어떤 arm의 실패율이 50%를 넘으면 해당 arm만 중단하고 원인을 기록합니다. 이것도 결과로 보고합니다.
- 누적 지출이 예산 상한에 도달하면 전체를 중단합니다. OpenRouter 실험 키에는 예산 한도를 걸어 둡니다.

### 독립성

- **Mango는 일반 고객과 같은 경로로 이용합니다.** 일반 가입·일반 선불 충전을 쓰고, 평가 중이라는 사실을 사전에 알리지 않는 방안을 권합니다. Mango에 평가용 크레딧을 요청하면 비용은 줄지만 특별 대우 가능성을 배제할 수 없습니다. 이 경우 보고서에 명시합니다.
- **(선택) 별도 계정 교차 측정:** 주 계정과 별개로 만든 두 번째 Mango 계정으로 W1을 회차마다 소량(모델당 5회) 같이 잽니다. 두 계정의 결과가 다르면 특정 계정 우대 가능성을 보고합니다. AA가 주 계정과 별개의 익명 계정으로 조작 여부를 검증하는 방식을 따른 것입니다.
- Mango 측에서 서버 측 지표를 따로 받으면 "제공사 제공값"으로 구분하고, 독립 측정값과 섞지 않습니다.
- 결과를 보기 전에 이 프로토콜을 제3자에게 검토받고, 검토자와 날짜를 13절에 기록하는 것을 권합니다.
